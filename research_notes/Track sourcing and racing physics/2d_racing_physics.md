# 2D racing physics for a deterministic RL environment

## Open-source repository findings and licensing

### Takeaway

The strongest licensed references are a spectrum: Dust Racing 2D is a custom, force-based dynamic/arcade racer; uRacer is a Box2D dynamic-body racer with a fixed 60 Hz loop and replay-oriented state; Screechy Rally is a Godot `RigidBody2D` drift racer. Small Pygame projects show cheaper kinematic patterns, while the most directly RL-oriented repository found (`track_racer`) is unlicensed and should be treated as inspiration only.

### Inferences

- For this project, the licensed repositories are most valuable as architecture references: Dust Racing 2D supplies a tire/grip decomposition, uRacer supplies fixed-step Box2D/replay boundaries, and Screechy Rally supplies a local-velocity drift model plus physics-frame records. These concepts can be independently reimplemented with different names, equations, and data structures. [Dust `Car`/`Tire`](https://github.com/juzzlin/DustRacing2D/blob/master/src/game/car.cpp), [uRacer `PhysicsStep`](https://github.com/manuelbua/uracer-kotd/blob/master/uracer-desktop/src/com/bitfire/uracer/game/logic/gametasks/PhysicsStep.java), [Screechy `CarDrift`](https://github.com/Pro1d/ScreechyRally/blob/main/scripts/CarDrift.gd)
- Unlicensed or unclear-license projects can still reveal useful state machines and reward/observation layouts, but they should not be treated as code sources. The RL-focused `track_racer` repository is the clearest example. [Metadata](https://api.github.com/repos/nikhil-ghind/track_racer)

### Gaps

- The inspected repositories do not provide a controlled benchmark of steps/second across Box2D, Pymunk, and custom vector implementations. Performance comparisons below are therefore engineering expectations, not measured results for this project.
- uRacer's actor base and `CarModel` expose the force interface and physical parameters, but the inspected repository snapshot did not expose a concrete player-car force subclass at the expected path. The notes distinguish what is directly visible (`Car.java` sets body velocities) from what is only suggested by the model fields.

## Physics patterns and technical references

### Takeaway

Use a fixed simulation clock and make all rates time-based. Box2D and Pymunk both recommend fixed stepping; Box2D 3.1 documents deterministic same-input reproduction and cross-platform determinism, while Pymunk emphasizes that a fixed step improves contact persistence and solver efficiency. A custom vector model avoids solver cost and is the most practical default for many parallel RL instances, provided collision and numerical rules are explicit.

### Cited Findings

- [Box2D Simulation documentation](https://box2d.org/documentation/md_simulation.html) recommends a fixed step, generally 1/30 s or smaller, with 1/60 s described as a usual high-quality choice. It defines static bodies as immovable terrain, kinematic bodies as user-velocity-driven objects that do not respond to forces, and dynamic bodies as finite-mass bodies moved by forces and torques. The same page documents sub-step counts and continuous collision/bullet handling.
- [Box2D FAQ](https://box2d.org/documentation/md_faq.html) states that Box2D is MIT-licensed, uses semi-implicit Euler and approximate iterative constraint solving, and is deterministic for the same input and binary; the FAQ says cross-platform determinism is available as of Box2D 3.1. It also notes that determinism can be broken by compiler flags and that Box2D does not provide rollback determinism.
- [Pymunk `Space.step` documentation](https://www.pymunk.org/en/latest/pymunk.html#pymunk.Space.step) says a fixed time step is highly recommended because contact persistence can require an order of magnitude fewer iterations in the usual case. The same API reference describes Pymunk as a Pythonic 2D rigid-body library and documents the default 10-iteration solver guidance for simple games.
- [Pymunk body documentation](https://www.pymunk.org/en/latest/pymunk.html#pymunk.Body) recommends applying forces when possible for stability, warns against changing a body's position every step, and distinguishes dynamic, kinematic, and static bodies. Its shape/arbiter documentation exposes Coulomb friction, surface velocity, collision normals, and collision impulses for custom grip/collision behavior.
- [Fix Your Timestep!](https://gafferongames.com/post/fix_your_timestep/) explains why variable `dt` changes simulation behavior, recommends a fixed-step accumulator to decouple rendering from physics, and warns that too many catch-up steps can create a “spiral of death.” It also explains interpolation from previous/current states for smooth rendering without changing the fixed simulation.
- [uRacer `Config.java`](https://github.com/manuelbua/uracer-kotd/blob/master/uracer-desktop/src/com/bitfire/uracer/configuration/Config.java) sets `TimestepHz = 60` and `Dt = 1/TimestepHz`; [its `PhysicsStep.java`](https://github.com/manuelbua/uracer-kotd/blob/master/uracer-desktop/src/com/bitfire/uracer/game/logic/gametasks/PhysicsStep.java) calls Box2D with that `Dt` and fixed solver iteration counts. This is a concrete racing-game example of the general fixed-step guidance.
- [Screechy Rally `CarDrift.gd`](https://github.com/Pro1d/ScreechyRally/blob/main/scripts/CarDrift.gd) calls the driving update from Godot's `_physics_process(delta)` and records controls/body states by integer physics frame. This is a practical replay pattern even if the Godot solver itself is not the recommended RL backend here.

### Inferences

- **Box2D:** best when the environment needs robust convex/segment collision, dynamic car-to-car impacts, sensors, or many static track fixtures. For a single car and static boundaries, the solver is more machinery than the RL policy needs; it should be an optional collision backend or validation mode rather than the default inner loop. This is an engineering inference from Box2D's documented world/body/contact/sub-step architecture, not a measured benchmark. [Simulation docs](https://box2d.org/documentation/md_simulation.html)
- **Pymunk:** a reasonable Python integration choice when true rigid-body contacts are central and the project wants callbacks, friction, impulses, and queries without writing a solver. Its fixed-step/contact-persistence guidance is favorable, but each environment step still passes through a general iterative solver; a custom core should be expected to have lower per-car overhead when the state is only one or a few vehicles. [Pymunk API](https://www.pymunk.org/en/latest/pymunk.html)
- **Custom vector physics:** best default for training throughput and exact control over determinism. A six-scalar vehicle state can model momentum, yaw, lateral slip, braking, and grip without broadphase/contact graph work. The boundary problem should be solved with a track-specific nearest-segment query and a small number of explicit correction rules, rather than a full general-purpose engine.
- Do not use wall-clock time, renderer frame rate, random spawning, or unordered entity iteration inside the transition function. Keep `step(action)` as: clamp action → integrate fixed `dt` → resolve boundary/collision → compute progress/reward → build observation. This ordering follows the fixed-step/replay patterns in Gaffer, uRacer, Screechy Rally, and the Gymnasium-oriented `track_racer` environment. [Gaffer](https://gafferongames.com/post/fix_your_timestep/), [uRacer](https://github.com/manuelbua/uracer-kotd/blob/master/uracer-desktop/src/com/bitfire/uracer/game/logic/gametasks/PhysicsStep.java), [Screechy](https://github.com/Pro1d/ScreechyRally/blob/main/scripts/CarDrift.gd), [RL environment](https://github.com/nikhil-ghind/track_racer/blob/master/env/racing_env.py)

### Gaps

- “Deterministic” depends on scope. Box2D documents same-input determinism for a given binary and cross-platform determinism in 3.1, but that does not prove deterministic behavior through every language binding, compiler, CPU, or vectorized RL runner. A project-level replay hash test is still needed.
- No source inspected here measures Python Pymunk throughput versus a NumPy/vectorized custom implementation. Benchmark the actual observation size, number of parallel environments, collision density, and ray-sensor count before committing to a backend.

## Recommended model for this RL project

### Takeaway

Implement a small, custom, deterministic **dynamic-feeling arcade model** rather than a general rigid-body solver. Use a fixed 60 Hz transition (`dt = 1/60`), a body-frame velocity with lateral slip, a damped yaw state, and a centerline/segment track representation. This retains the learning-relevant consequences of momentum, acceleration/braking, steering, friction, slip, and boundaries while keeping each environment step predictable and cheap.

### Cited Findings

- A two-state scalar baseline is demonstrably cheap: `track_racer` uses only position, heading, speed, direct acceleration/braking/friction, and a ray loop; its tests cover throttle, braking, ray ranges, Gymnasium return types, and off-track termination. [Car](https://github.com/nikhil-ghind/track_racer/blob/master/env/car.py), [environment](https://github.com/nikhil-ghind/track_racer/blob/master/env/racing_env.py), [tests](https://github.com/nikhil-ghind/track_racer/tree/master/tests)
- A useful next step is visible in the licensed references: Dust Racing 2D separates longitudinal drive from lateral tire projection and off-track grip, while Screechy Rally tracks local longitudinal/lateral relative velocity, drift thresholds, and yaw impulses. [Dust tire model](https://github.com/juzzlin/DustRacing2D/blob/master/src/game/tire.cpp), [Screechy drift model](https://github.com/Pro1d/ScreechyRally/blob/main/scripts/CarDrift.gd)
- Fixed-step replay/state capture is already used by uRacer and Screechy Rally: uRacer stores fixed `Dt` physics data, and Screechy stores control/body-state records keyed by physics frame. [uRacer replay/physics](https://github.com/manuelbua/uracer-kotd/blob/master/uracer-desktop/src/com/bitfire/uracer/game/logic/gametasks/PhysicsStep.java), [Screechy records](https://github.com/Pro1d/ScreechyRally/blob/main/scripts/CarDrift.gd)

### Proposed state and transition

Use state:

- `p = (x, y)` world position.
- `theta` heading angle and `omega` yaw rate.
- `u` forward velocity and `v` lateral velocity in the car frame.
- Optional progress/checkpoint index and a deterministic `off_track_time` accumulator kept by the environment, not the vehicle.

At each fixed step, with normalized action `(steer, throttle, brake)` or `(steer, signed_accel)`:

1. Clamp action components to `[-1, 1]`; do not use random numbers in the transition.
2. Convert local velocity to world velocity using the heading basis.
3. Apply drive/brake and speed-dependent drag to `u`. Use a bounded engine acceleration and a stronger brake acceleration; keep reverse as an explicit design choice rather than an accidental negative-speed case.
4. Apply lateral grip as a bounded decay of `v`, with a lower coefficient on grass/oil/off-track surfaces. Add a small steering-induced lateral/yaw term proportional to forward speed so steering has little effect while stationary and strong effect at speed.
5. Update `omega` toward a steering-dependent target, with yaw damping and a grip-dependent slip term. Update `theta += omega * dt`, then integrate position from the world velocity. Semi-implicit Euler is sufficient for this bounded arcade model; Box2D's FAQ identifies the same integrator family as a practical approximation. [Box2D FAQ](https://box2d.org/documentation/md_faq.html)
6. Query the nearest centerline segment, signed lateral error, and tangent. Use the signed error for observations/progress and the track width for boundaries. A segment spatial index or fixed waypoint window avoids scanning every segment for every ray/environment when tracks grow.
7. Resolve boundaries deterministically. If the car penetrates a wall, push it back along the segment normal, remove the outward normal component of velocity, reduce tangential speed by a configurable impact loss, and emit a collision flag. For an arcade-only boundary, terminal off-track is cheaper; offer “bounce,” “scrub,” and “terminate” as explicit modes.
8. Compute reward and observation after correction. Keep ray sensors optional because nine rays at 200 samples each, as in `track_racer`, can dominate a tiny physics update; use analytic segment/ray intersection or a downsampled distance field instead of pixel marching when scaling to many environments. [RL ray implementation](https://github.com/nikhil-ghind/track_racer/blob/master/env/car.py)

Recommended initial constants are qualitative rather than copied values: `dt = 1/60`, forward acceleration that reaches top speed over roughly 2–4 seconds, brake acceleration about 1.5–2.5× drive acceleration, linear and quadratic drag, lateral grip high enough to recover normal driving but low enough that a sharp steering/brake input produces visible slip, and off-track grip/speed loss rather than an invisible hard teleport. Tune these from short deterministic scenarios (straight acceleration, coast, full brake, constant-radius turn, steer-release recovery, wall hit, and off-track return).

### Backend decision

1. **Default:** pure custom vector core in Python, with scalar code first and a batched NumPy path once behavior is validated. It has no solver iterations, no general contact graph, and makes replay hashing straightforward.
2. **Optional:** Pymunk for a debug/validation environment or if the project later adds dynamic obstacles and car-to-car collisions. Keep `Space.step(fixed_dt)` and avoid setting body positions each frame; use forces/impulses and collision callbacks as documented. [Pymunk body guidance](https://www.pymunk.org/en/latest/pymunk.html#pymunk.Body), [Pymunk stepping](https://www.pymunk.org/en/latest/pymunk.html#pymunk.Space.step)
3. **Use Box2D only when its collision features justify the cost:** multiple dynamic cars, complex static geometry, bullet/CCD requirements, or direct parity with an existing Box2D game. If used, create static chain/segment boundaries, one dynamic body per car, fixed 60 Hz stepping, fixed solver settings, and no renderer-dependent updates. [Box2D simulation](https://box2d.org/documentation/md_simulation.html)

### Determinism and verification checklist

- Run the same seed and action sequence twice and compare every state/reward/termination bit; also hash serialized state every N steps.
- Test with rendering disabled and at different render-loop rates; results must be identical because render time is not simulation time. [Gaffer](https://gafferongames.com/post/fix_your_timestep/)
- Preserve creation/order rules for multi-car environments and avoid unordered collections in collision/progress resolution. Box2D explicitly notes creation order in its determinism discussion. [Box2D determinism](https://box2d.org/documentation/md_simulation.html#determinism)
- Include edge cases: zero speed with full steering, reverse/braking sign changes, high-speed wall impact, grazing a boundary, crossing a checkpoint backward, exact start-line crossing, and a ray whose endpoint lands exactly on a segment.
- Record versioned physics parameters and a transition schema with every trained policy. A changed `dt`, collision correction, friction law, or track geometry should invalidate old replay comparisons.

### Inferences

- The recommended six-state model is the smallest practical compromise between the scalar `track_racer` baseline and the more expressive tire/drift patterns in Dust Racing 2D and Screechy Rally. It should be substantially cheaper than invoking a general solver for every agent while preserving the action consequences that matter for racing policy learning. This is a design recommendation, not a measured performance claim. [Scalar baseline](https://github.com/nikhil-ghind/track_racer/blob/master/env/car.py), [Dust tire forces](https://github.com/juzzlin/DustRacing2D/blob/master/src/game/tire.cpp), [Screechy drift](https://github.com/Pro1d/ScreechyRally/blob/main/scripts/CarDrift.gd)
- A fixed 60 Hz core with action repeat/frame skip at the Gymnasium level is preferable to lowering the physics rate: the agent can act every 2–4 physics ticks while collision and slip remain stable. This follows the fixed-step guidance and the racing examples' 60 Hz choices. [Box2D](https://box2d.org/documentation/md_simulation.html), [uRacer](https://github.com/manuelbua/uracer-kotd/blob/master/uracer-desktop/src/com/bitfire/uracer/configuration/Config.java)

### Gaps

- The project still needs an empirical benchmark comparing: custom scalar, custom batched NumPy, Pymunk, and Box2D; 1/60 versus 1/120; analytic versus sampled ray sensors; and one versus many cars. Use steps/second, wall-clock time per million transitions, replay hash stability, and learning curves as acceptance metrics.
- Exact friction, yaw, boundary restitution, reward weights, and action-repeat values should be tuned against the project's intended track geometry and agent observation space rather than copied from any reference repository.
